# Developing the Encounter Builder

How the code works and why, for anyone changing it. What it does for a GM is in the README.

## Layout

| File | Role | Foundry globals? |
|---|---|---|
| `scripts/brief.mjs` | The brief: `cleanBrief` fills and range-checks it, `expandCreatures` gives one entry per creature | no |
| `scripts/budget.mjs` | Treasure tables, `adjustedLevel`, the running total (`ledgerLine`), `chooseTreasure`, claim and party size notes | no |
| `scripts/journal.mjs` | `journalPages`: the journal as page data. Brief text is escaped here | no |
| `scripts/mapread.mjs` | `buildModel`: the per-square model (footing, cover, exposure, approach, anchors) and its `sees` and `fits` tests; `summarise` | no |
| `scripts/place.mjs` | `layout`: scoring and placement; `nearestFree`, `hiddenNextTo` | no |
| `scripts/builder.mjs` | Gathers documents (`readMap`), resolves creatures, `prepare` (plans, creates nothing), `place`, `clear`, `prepareReplace`, `applyReplace`, previews | yes |
| `scripts/turn.mjs` | A monster's turn as data: `checkPlan` (legality), `describeStep`, `nextAction`, `nextMove`, `nextPosture`, `nextCover`, `nextAbility`, `nextSpell` and `nextArea` (where a step stands); spells: `areaHurt`, `aimText`, `SAVE_MULT`, `spellMultiplier`, `spellActions`, `spellRange`, `spellTargets`; `isMove`, `POSTURES`, `absorbOwn`, `damageOptions`; Take Cover's `coverAfterTaking` and `endsCover`; abilities: `FOLLOW_UPS`, `CHECK_WORD`, `abilityCost`, `lastAction`, `followUpOutcome`; one action at a time: `situationOf`, `changesSince`, `describeChange`, `spentBy`, `doneStep`; `listWords` | no |

| `scripts/move.mjs` | Moving: `distanceBetween` (PF2e's distance between two creatures), `findRoute` (a Stride's route and cost), `findStep` (a Step's), `footprintAt`, `routeWords`, `headingOf`, `featureNear` (a wall next to a creature's space, for Take Cover) | no |
| `scripts/perceive.mjs` | What a monster perceives: `perceiveOne` (the state for one pair), `sensesOf`, `lightAt`, `packetOf` (the only way anything about others gets into a packet), memory, labels, health words, ability text as plain words | no |
| `scripts/brain.mjs` | The brain interface: `cleanPlan` and `cleanMeta` (a plan and who made it, from outside), the event queue (`nextSeq`, `live`, `pickEvent`, `eventOut`), `listening`, `stale` generations, `hello` | no |
| `scripts/prompt.mjs` | `promptText`: the thinker's instructions, the same for a chat and the API | no |
| `scripts/fight.mjs` | The runner, turn requests on the Combat flag, gathering what a monster senses (`sense`, `buildPacket`), `submitPlan`, `judge`, `doIt`, one action at a time (`runTurn`, `lookAgain`, `replan`), the world a Stride or Step moves in (`mover`, `cantMove`), carrying out a Stride, Step or Crawl (`runStride`), a Stand or Drop Prone (`runPosture`), Take Cover (`runTakeCover`, `takeCover`, ending it with `settleCover` and `endTakeCover`), an ability (`abilityList`, `runAbility`), a spell (`spellBook`, `spellsOf`, `runSpell`, `awaitSave`, `savedDegree`, `saveButton`, `rollSaveOnCard`, `rollFor`, `onMessageUpdate`, `leaveWaiting`), an area spell (`areaCheck`, `coverage`, `solidWalls`, `shapePx`, `placeArea`, `runArea`, `awaitAreaSaves`, `rollSavesOnCard`, `aimAll`, `dropInstantAreas`) and a Strike, applying damage | yes |
| `scripts/ui/build.mjs` | The Build Encounter window and the preview loop | yes |
| `scripts/ui/turns.mjs` | The Monster Turns window: who's ticked, and the plan card. It shows the fight on the scene this browser is viewing, so `main.mjs` redraws it on `canvasReady`, a fight or combatant created, updated or deleted, a token deleted, a token's module flags (another GM ticking a box) and every `updateCombat` that matters (0.5.1; before that a scene change left it saying "No fight on this scene") | yes |
| `scripts/main.mjs` | Settings, the left-bar group "Encounters", hooks, API | yes |

The plan's `legal.mjs` is `checkPlan` in `turn.mjs` for now, and covers Strikes, Strides, Steps, Crawls, Stand, Drop Prone, Take Cover, abilities and spells.

## Data

All flags use the module id as their scope: a made-up scope throws.
- **Scene:** `brief` (the last brief, or one sent from a chat), `build` (`id`, `seed`, `threat`, `rev`, `at`, `entry` the journal id), `design` (a request from Ask Angel with the map summary).
- **Tokens:** `built`, `key`, `group`, `role`, `run`, `auto`, `model`, `opus`; `cache` on a cache's token. Per token, not actor, so each monster has its own checkbox later.
- **Actors, journal, notes:** `built`. Folders carry `own`.
- **Combat:** `turns.requests`, one per monster turn: `state`, `combatantId`, `tokenId`, `round`, `turn`, `labels` (E1 and so on, to token ids: only what it perceived at the time), `packet`, `plan`, `by` (who made the plan: route, model, generation, usage), `tries`, `gaveUp`, `steps`, `verdict`, `note`, `go`, `hold`, and `log` by step; `pos` (the next step), `seen` (what the plan rests on, taken with the packet); on a re-plan also `spent` and `attacks` (what earlier requests this turn used), `done` (what it did, in labels), `replans`, `why` (the changes, as data) and `parent`, and the old request gets `replanned`. `turns.events`, by number: `seq`, `kind` (`turn`, `retry` or `replan`), `requestId`, `tries`. `turns.labels`, token id to label, kept for the whole fight. `turns.memory`, by monster token then enemy token: `square` and `round` it last perceived them. `turns.grips`, by monster token then target token: `round`, a grip its own Grab made (for Grab's hold). On a request, `rollFor` (token id: true) is a GM's Roll it for them for a save still waiting. It all goes with the fight.
- **World settings:** `partySize`, `applyMonsterDamage`, `autoPause` and `runner` (in the settings menu), `treasure` (`manual` by level, `builds` by id), `brain` (`generation`: who is thinking; its old `at` is no longer read) and `brainAt` (when the thinker last asked).
- **Every document a build makes carries `built` = its id.** `clear` deletes only those, by id, so hand-placed things and Survey Sheet's documents stay. A build's actors stay if a token on any scene still uses them.

## Reading the map
`surveyRead` calls `api.readEncounterMap` on Lythara Survey Sheet and caches by `rev` and heading, because the read's `entry` follows a live setting. It refuses a `schema` it doesn't know, with a plain message. If the module is missing or too old, or the scene isn't one of its maps, the read is null and the model is partial: walls and regions only, entry at the south edge, no anchors.

**The documents are the truth for anything a GM can edit.** Walls and movement costs come from the scene, not the read, so a hand-drawn wall or region counts. The read supplies what documents can't say: brush, canopy, anchors, the party's heading.

`entry` comes from the party's tokens if any are on the map, otherwise from the read. The preview says which.

## The model
- **Geometry is in squares, y down,** relative to the map's corner, so Extend's changed offsets don't matter once gathered.
- **`sees`** copies core's rules for what Survey Sheet makes: past one limited wall yes, past two no, a blocking wall stops it. **One-way rings count once:** with `dir` LEFT and vertices clockwise on screen, a point outside has a negative cross product (`facing`). `crosses` is half-open, so a line through a ring's corner still counts once. Core's own sight test needs the canvas on that scene; the pure copy doesn't, so it works from the bridge or with the map closed. On a real woods map it agreed with core's `testCollision` on 2,997 of 3,000 random pairs (the rest grazed a wall's end), which also shows core counts one-way rings as a single wall.
- **`blocked`:** a movement wall crosses the square's middle 70%, so a token doesn't stand on a trunk.
- **`exposure`:** the share of the party's starting squares that can see this square. Five samples around a single entry square, so "in view" isn't judged from one point.
- **`approach`:** walking feet from the entry by Dijkstra, doubling for difficult and tripling for greater, diagonals half as much again (the 5-10 rule, averaged).
- **Height is advisory:** a map is one level, so tokens stay at elevation 0 and high ground has no rules effect.

## Placing
`layout` scores every square that fits for each creature in role order (guard, brute, ambusher, beast, ranged, caster), so the back line can read where the front went. Same model, creatures and seed give the same layout: "Try another layout" only adds 1 to the seed.
- **First a strict pass:** a creature that doesn't start alert avoids every square the party can see. If nothing fits, a second pass allows them and warns.
- **A guard stays by what it guards** (within `GUARD_REACH` squares), in view or not, and the warning says so. Otherwise a camp in plain sight sent its guard to the far side of the map.
- **`MOOD_WINDOW`** sets the walking distance from the entry: first contact by about round 2. These are starting points to judge on samples.
- **Never** in a wall, on a token, on a footprint that doesn't fit, in deep water without a swim speed, or within 15 ft of walking from the entry.

## The numbers
- **XP is PF2e's `calculateXP`.** Before placing, levels come from `adjustedLevel`; after placing, from the real tokens. If the rating changes the report says so.
- **Party level is never taken silently from the Party actor,** which reports a level no member has. `suggestedLevel` is the sheets' most common level, and the window shows the sheets and asks.
- **Treasure:** the brief's list first; otherwise Treasure by Encounter (GM Core, https://2e.aonprd.com/Rules.aspx?ID=2738) with Treasure by Level's totals (https://2e.aonprd.com/Rules.aspx?ID=2656). Trivial has no column, so it places none. `chooseTreasure` keeps it sensible: nothing for animals and other things with `NO_CARRY` traits, a cache for a lair. Items are common, within a level of the party's: healing potions and elixirs, and talismans, from the equipment pack; a lair's goods are gems and art from KCTG Trade Goods and the equipment pack, by category, because KCTG's other treasure includes livestock and rubble.
- **`chooseTreasure` doesn't pick permanent items.** The rule borrows their value from other encounters, so those are the GM's or the brief's to place.

## Placing documents
- `prepare` creates nothing, and ignores the tokens and treasure of the build it would replace. `place` clears the old build first.
- **Tokens are unlinked and the imported actors are copies.** One world actor per creature and adjustment per build, in the "Encounter Builder" folder, never a compendium original. Adjustments use `applyAdjustment` on the copy. Items and coins go on the token's own actor, so each creature carries its own. Conditions for asleep use the token's actor too.
- **A cache** is a loot actor with a core-hidden token. PF2e sets loot actors to LIMITED for all whatever is asked for, which is enough for a player to open it once revealed. Visioner's per-token Stealth DC isn't set by the builder yet.
- **The journal** has no ownership by default. GM truth goes in `section.secret`. Tactics is a page of its own because monster turns will read it each turn, so editing it mid-fight changes the fight. With no brief text it holds only the maths and creature list: it makes up no story.
- **Map notes** only where the brief asks, each with its own page. **A clue players may find has OBSERVER on its page, not LIMITED:** core's `Note#_canView` refuses a page with exact LIMITED unless it's an image, and a double-click then does nothing (tested 14.370). LIMITED on the journal itself would list it in their sidebar, so the journal stays at none and an `activateNote` hook shows the page in a small window, with its @Check links working.
- **Foundry's redraw rule:** never create placeables while a client redraws (see Survey Sheet's DEVELOPING.md). `canvasSettled` waits for `canvasReady` when the GM's canvas is on that scene and a draw just happened.
- **Survey Sheet's redraw** removes only its own `enc` documents, and its Extend shifts everything else, so builder documents move with the map.

## A monster's turn (so far: Strides, Steps, Crawls, Stand, Drop Prone, Take Cover, abilities, spells, area spells, Hide, Sneak, Seek and Strikes, one at a time)
- **The runner does the work.** The `runner` setting names one GM account, Claude Bridge by default. Only that account's page creates requests, judges plans and carries out turns. Any other GM's Do it writes `go` on the request and the runner picks it up from `updateCombat`. If the runner is offline or doesn't exist, `runnerProblem` gives the words, the card shows them, Do it is disabled, and nothing runs anywhere else. Foundry's active GM can't be chosen, which is why the module names its own. PF2e's and Workbench's own automations still run on the active GM.
- **A turn starts:** the runner sees `turn` or `round` change in `updateCombat`, because `pf2e.startTurn` fires on the active GM only. Also when a monster is ticked during its own turn, and when the runner's page loads. A short wait, then a request in state `requested`. How long start-of-turn effects really need is still to be measured.
- **By round and combatant, not turn number.** Workbench moves a PC's initiative at 0 HP, which changes `combat.turn` in the middle of a monster's turn. `currentOf` and the guard in `onTurnChange` use the combatant so that doesn't start a second request or hide the card.
- **The scene:** `ensureScene` opens the fight scene on the runner before anything that uses the canvas, because activating any scene pulls that page along and Visioner answers "observed" for tokens it can't find. A view takes about 1 to 3 s. Map jobs (a sheet redraw, the exploration carry) don't move the view and a Strike during one wasn't slowed (measured 2026-11-05). If it can't open, the card says so.
- **The plan:** any GM may call `api.fight.submitPlan`; the runner's `judge` checks it. `ready` shows the card.
- **One action at a time (Rhea, 2026-11-06).** `runTurn` carries out one step, saves `pos`, then: without Auto it stops at `ready` and the card's button reads **Next step**; with Auto it waits `autoPause` seconds (Hold and Play it myself end the wait at once) and goes on. She chose this after a three-bite turn scrolled past too fast to follow.
- **Look again before each action (`lookAgain`).** `seen` is taken with the packet, because that's what the plan was made from. Before any step that hasn't begun, `changesSince` compares it with now: the monster's square, HP (with temporary HP), actions this turn and conditions; and for each creature it could name, its square, how it's perceived and whether it's down (no HP, dying, unconscious or dead). The monster's own Strikes lowering someone's HP don't count, but someone going down does. Then `checkPlan` runs on the rest of the plan with what's left. **Anything at all → `replan`:** the request ends (`done`, `replanned`), and a new one for the same turn gets a fresh packet with `actionsLeft` less what's spent, `attacksMade`, `done` and a `note`, its own `seen`, and a `replan` event. The multiple attack penalty carries on through `attacks`. No actions left ends the turn with a note; a fourth re-plan in one turn (`MAX_REPLANS`) goes to the GM. Notes stay with the turn: Next step keeps a note from an earlier step (only a held or stopped turn's note is cleared when it goes on), and after the turn the card shows the notes of every part of a re-planned turn (`latestNote` follows `parent`). A step begun before a reload carries on from its log and is never re-planned halfway. A reaction isn't tracked as such: what it does (HP, conditions, a move) is what counts.
- **The turn stays with the monster when it drops a PC (`keepTurn`, 0.4.4).** Workbench moves a PC at 0 HP to just ahead of whoever's turn it is, in its `preUpdateActor` hook, so on the page that applied the damage: the runner's. PF2e's `setMultipleInitiatives` then sets `turn` to keep the current combatant, but that page's own copy has often already shifted, so the update finds nothing to send and the server keeps the old turn number: the PC became current mid-turn and the monster's end of turn fired (2026-11-06: 2 in 4 real turns with AI live as active GM, 3 in 3 with the Bridge itself as active GM). On the runner's page, whether or not it's the active GM, `keepTurn` (a `preUpdateCombatant` hook) adds core's own `combatTurn` (where the current combatant will sit, from `_sortCombatants` on clones with the change) and `turnEvents: false`, as core's `rollInitiative` does, so every page keeps the same creature current with no turn event. **Core applies `combatTurn` only in each page's copy and never saves it** (the server kept the old number and every page fell back to it), so `saveTurn` (an `updateCombatant` hook on the same page) then saves the turn with `diff: false`, because the runner's own copy already matches. Tested by hand before the release: real monster turns lost the turn 2 times in 4 without it, and 6 in 6 kept it with both hooks; AI's page fired no turn event.
- **Strides (0.4.6).** A plan step `{ do: "stride", to: [x, y] }`, squares being map squares from the top-left (a creature's square is its top-left one). `checkPlan` replays the plan from where the monster stands: a Stride moves where every later step is measured from, and costs an action.
  - **Distance** is `distanceBetween`, a copy of PF2e's `measureDistanceCuboid`, height included (at different elevations the vertical gap is a third axis, from elevation and the token's depth; 0.4.6 left it out, so a ground monster could have bitten a flyer): squares between the creatures' edges, every second diagonal double, and with reach 10 five feet off when the line has more than one diagonal (10-foot reach reaches two squares diagonally). It matched `distanceTo` on 32 pairs, Medium and Large (2026-11-07). **Off the grid (0.8.3):** x and y may be fractional, and as PF2e does it tests overlap on where the creatures really are, then snaps each one's edges to the grid toward the other before counting. `gather` gives each creature `pos` (`posOf`, unrounded squares) beside its rounded `square`; `checkPlan` measures from the monster's `pos` until a move step puts it on a square, to each target's `pos`. Routes, occupancy and the square the thinker is told stay rounded. Checked against PF2e's own `measureDistanceCuboid`, run on the server with a stub grid, on 36,864 cases (Medium and Large, quarter-square offsets, reach 10 on and off): no difference. Melee is checked with the Strike's reach passed in, as PF2e does; before 0.4.6 the check used plain `distanceTo`, which refused a Dire Wolf two squares away diagonally.
  - **Only creatures it knows of shape the route it's told about:** allies the GM hasn't hidden, and those it perceives well enough to know their square (observed, concealed, hidden). 0.4.6 counted every creature, so a refusal ("another creature is at…", a longer route, "no way") could give away an invisible PC or a GM-hidden token (found by an independent review). On the move itself, `cutShort` ends it before the space of a creature it didn't know of, as the rules say for moving into an undetected creature's space; with steps left the thinker is asked again with "It was stopped at [x, y], short of where it was going.", never why. The GM's card names the square.
  - **The route:** Foundry has no pathfinding (`Token#findMovementPath` only adds terrain waypoints and stops at walls), so `findRoute` searches the squares: Dijkstra over square and whether an odd number of diagonals has been taken, never through an enemy's space (an ally's is fine), never ending on anyone, never into a square `readMap` calls blocked (a trunk in its middle), never into deep water, and walls by core's own movement test between where the creature's centre would be (`mover`). Difficult squares add 5 ft and greater 10, which is what Foundry charged. **The diagonal count runs across the whole turn** (Rules ID 444, https://2e.aonprd.com/Rules.aspx?ID=444), and Foundry agrees: it keeps the token's `movementHistory` for the turn (empty again when the turn changes) and charges a new move as the rest of that path. 0.4.6 measured each Stride on its own and said 10 ft for a move Foundry charged 15, after an earlier Stride with an odd number of diagonals. So `mover` measures the history plus this plan's earlier Strides plus the new route, less the same without it, and `findRoute` starts with the diagonal count they leave (`odd`). A history segment can span several squares (a hand-dragged move), so `diagonalsIn` counts min(|dx|, |dy|) per segment.
  - **The cost that counts is Foundry's:** `measureMovementPath` on `createTerrainMovementPath` of the route, with `TerrainData.getMovementCostFunction`. On 5 routes over difficult terrain that equalled what a real `move` charged in `moveToken` (`passed.cost`), and on a real map it equalled `findRoute`'s count for all 223 squares a Medium creature could reach. For a Large creature Foundry charged 5 ft less on 28 of 219 (it seems to test terrain at the token's centre, not each square), so the route may not be the very cheapest by Foundry's count, but the figure compared with Speed is always Foundry's.
  - **Deep water:** Survey Sheet's greater-difficult regions are named "Deep water"; a Stride can't enter those squares (swimming is its own action). Other greater difficult terrain just costs 10 ft more.
  - **Moves are worked out only for a plan with a Stride or Step** (`gather`'s `moves`), and a failure there refuses the Stride in words, so it can't stop a plan of Strikes. A square past where the search looks (four times Speed and 60 ft) is "far beyond its Speed", not "no way".
  - **Can't act at all** (`cantAct`): dead, paralyzed, petrified, unconscious. Every step but `none` is refused. **Can't use move actions** (`cantMove`: Stride, Step, Crawl, Stand and Drop Prone): restrained, grabbed, immobilized (named in that order, because PF2e adds Immobilized with them; Immobilized bars every action with the move trait). **Prone and no land Speed are `checkPlan`'s,** because a Stand or Drop Prone earlier in the plan changes it: `gather` passes `prone`, and the replay refuses a Stride or Step while it's prone and a Crawl while it isn't. Speed is `system.movement.speeds.land.value`.
  - **Carrying it out (`runStride`):** `TokenDocument#move` with every square of the route as a waypoint and the token's own `movementAction` (walk in a fight). It waits for the `moveToken` hook, which comes before the document's position changes, then for the position and the animation, because cover and sight are read from where the token is drawn. `log` gets `started`, then `moved` with where it ended and the cost charged. A move begun before a reload is never sent again: if the monster is where it was going it counts as done, otherwise the GM looks. Scripted moves work while the game is paused (tested).
  - **The route is checked again just before the move:** the look before each action runs `checkPlan` on the rest of the plan, and a Stride then follows the route that check found (saved over the step, with its cost), not the one found when the plan came in. The ground can change without the monster noticing: a wall, or a creature it doesn't perceive stepping onto the old route.
  - **A look that fails** (an error while checking the next step) stops the turn with a note instead of leaving it "running".
  - **One save for a step's end:** the step's `log` record and the baseline's change (`seen.me.square` after a move, `seen.me.conditions` after a Stand or Drop Prone) go in the same save, so a reload between them can't leave the step done with the old baseline and a re-plan for its own action (found by the 0.5.1 review; 0.5.0 saved them apart).
  - **Its own Stride isn't news:** afterwards `seen.me.square` is set (only when the request has a baseline: one from before 0.4.0 or with no packet has none) to where it stands, so the look before the next action doesn't re-plan because it moved. Everything else still counts, including someone now seen differently from the new square (a fresh think, with the right flat check), an HP change from a reaction, and stopping short (the rest of the plan is checked from where it really is).
- **Steps (0.5.0).** `{ do: "step", to: [x, y] }`: one square, 5 ft (Rules: https://2e.aonprd.com/Actions.aspx?ID=2304). It goes through everything a Stride does (`mover` with `{ step: true }`, `runStride`, the look before it, `cutShort`, the re-plan when stopped short), with `findStep` in place of `findRoute`: the square must be next to it, free, not solid, not deep water, and **no square it enters may be difficult** (a Large creature's old squares don't count); a wall between the centres refuses it. It needs a land Speed of at least 10 ft. **A diagonal Step after an odd number of diagonals this turn is refused:** the 5-10 count runs across all movement in the turn (Rules ID 444), Foundry would charge 10 ft for it, and a Step moves only 5 ft; `checkPlan` compares Foundry's figure with 5. A Step triggers no reactions, so when reactions are built it gets no gates.
- **Crawl (0.5.1).** `{ do: "crawl", to: [x, y] }`: Player Core's Crawl, only while prone, Speed 10+, one square, staying prone. It goes through the Step's path (`findStep`, `runStride`), moving and priced with Foundry's `crawl` action because a prone token can't walk (PF2e's `canSelect`), while a Stride or Step never goes as a crawl (`moveAction`); the check measures it with the terrain cost alone, which is the rules distance (5 ft a square, 10 for difficult terrain or a second diagonal), so anything over 5 ft is refused, difficult terrain included. **Foundry's own crawl action doubles what it books** (core's `costMultiplier: 2`), so a real Crawl's `moved.cost` reads 10 ft for one square; that is Foundry's bookkeeping, not the rules, and nothing else depends on it (a Stride after a Crawl was priced and charged correctly, tested 2026-11-07). Unlike a Step it can trigger reactions when they're built.
- **Stand and Drop Prone (0.5.0, 0.5.1).** `{ do: "stand" }` only when prone, `{ do: "drop-prone" }` only when not, and not above the ground, where it would fall instead (Rules: Prone, https://2e.aonprd.com/Conditions.aspx?ID=88). `runPosture` uses PF2e's own action (`game.pf2e.actions.get(kind).use({ actors })`, `StandActionVariant` and `DropProneActionVariant` in PF2e 8.7.0), which posts the action's card and toggles Prone, with no dialog. Then it waits up to 2 s for Prone to change (PF2e awaits its own toggle, so this is a margin). `log` gets `started`, then `changed`; one begun before a reload is never sent again (`nextPosture`, which also reads 0.5.0's `stood`): already as the step leaves it counts as done, otherwise the GM looks; not begun and already like that is done with nothing posted. Afterwards `absorbOwn` puts into `seen.me.conditions` what the action itself changed, limited to Prone and the Off-Guard it brings, so the look before the next action doesn't re-plan for its own doing while a condition a reaction added still counts (0.5.0's first draft copied all conditions, which the review caught).
- **Take Cover (0.5.2).** `{ do: "take-cover" }`, 1 action (Rules: https://2e.aonprd.com/Actions.aspx?ID=2307). Rhea, 2026-11-07:
  - **When it's allowed (her rule B):** prone, or a wall or thick trunk next to its space (`featureNear`: a segment through the ring of squares round it, more than a touch at a corner), or standard or greater cover from a creature it sees and could name. `checkPlan` replays it: not while already Taking Cover (`tookCover`), and a Strike or a move earlier in the plan ends one so it may be taken again; after a move only a wall next to the new square counts, because cover from a square it isn't on yet can't be read. One taken while prone ends on a Stand in the plan. The packet's `you.takeCover` (`taking`, `nextToCover`, `standardCoverFrom` as labels) tells the thinker the same.
  - **Which walls (`nearCoverFor`):** those Visioner gives cover from (its `CoverDetector`, 8.14.17): blocking sight, or set to standard or greater cover. Not an open door, not one set to lesser or none or "no cover" (`provideCover: false`), so Survey Sheet's thin trunks (under 3 ft, lesser) don't count: Rhea's rule. A movement-only wall (a fallen stone with sight none) counts only if it's set to give cover. **Known gap:** an invisible wall round a map's edge blocks sight, so it counts.
  - **What it does: Visioner's per-creature cover (her option 1).** PF2e's own "Effect: Cover" gives one bonus against everyone, takes the higher of it and Visioner's wall cover rather than adding (AC 15 behind a thick trunk was 17 with it at standard), and never ends by itself. That re-ask doesn't count toward `MAX_REPLANS` (`replan(..., { counted: false })`), and nothing is saved between the Seek's record and the re-ask, so a reload there reaches the re-ask again.
  - **A Sneak's start:** Visioner's Start Sneak records each creature's start as `observer.document.canObserve(...) ? "observed" : "hidden"` when its automatic system is off, and Foundry 14 has no `canObserve`, so every start read "hidden" and a Sneak could make the monster hidden from creatures that saw it (Valeros went observed to hidden, 2026-11-07). `fixSneakStart` puts Visioner's own stored `getVisibility(observer, monster)` back into the card's `sneakStartStates` and `startStates` before the move, after waiting for all three of Start Sneak's writes (`sneakStartStates`, `sneakStartPosition`, then `startStates`, which its results window reads). No record counts as observed, which is what the GM's records say, even when the module's own perception would call the monster unseen by that creature. The move itself is `runStride` on the same log entry (`started`, `moved`), at most half Speed (`sneakSpeed`, Visioner's own rounding).
  - **The record (`nextStealth`):** `rollStarted`, `card`, then for a Sneak `startStarted`, `startDone` and the move, then `applyStarted`, `applied` (`"applied"` or `"none"`); `gm` hands it over. A reload after Apply was pressed reads the card (`check`): Revert there means done, otherwise the GM looks. Nothing is pressed twice.
  - **What the monster knows (Rhea chose B):** `you.stealth` says what it last tried and that it hasn't come out of hiding since (`turns.stealth`, kept by the module), the light where it stands, its own concealment and who it has standard cover from; never whether the secret roll worked. `doneStep` says "hid (whether it worked is secret)". `checkPlan` refuses a Hide with nothing to hide behind as far as the monster knows (standard cover from a creature it sees, Taking Cover, concealed, or dim light or darkness; after a move only a wall or trunk next to it or the light there); Visioner checks each creature when it applies. A Sneak needs no proof it started hidden, because the monster can't know: Visioner rolls only against those it was hidden from.
  - **Coming out of hiding (Rhea chose A):** `revealsBefore`: anything but Hide, Sneak, Step or an attack makes the monster observed, just before it, by every non-allied creature that has it hidden, undetected or unnoticed in Visioner (`comeOut`, through Visioner's public `setVisibility`), with a note on the card; `revealsAfter`: an attack does so after (its off-guard came from Visioner during the roll), pressing Visioner's own `apply-now-consequences` on the attack card first where it is there. With Visioner's automatic system on, the card notes it and Visioner decides. `turns.stealth` is forgotten then.
  - **No target in the check:** `stopAiming` before PF2e's action, which would otherwise take a target left from an earlier step into the check's roll options.
  - **The thinker's memory of trying:** `turns.stealth` is cleared by any revealing action (`comeOut` runs for every such step and clears it first), whether or not anyone had the monster hidden; clearing it only when someone did would tell the thinker a failed Hide (found by the review). The packet words it as "has only Hidden, Sneaked or Stepped since", never "still hidden".
- **Not built yet:** reactions to a move (Reactive Strike when it leaves reach, during a Crawl or a Sneak, and at the end of a Stand or Drop Prone: Rules ID 446), other speeds, Interact, Delay; feats that change Sneak's speed (Swift Sneak) for the module's own check.
- **Words the thinker reads use labels.** Refusals, change reasons and notes about targets are written with E and M labels (`gather` names targets by label), so nothing sends a PC's name to the thinker; the card swaps the labels for names when it draws them. Retry reasons carried names before 0.4.0.
- **`api.fight.busy()`** says whether a turn is being worked on or about to be, for tools that share the runner's page (bridge 0.2.0). It counts `requestBusy` on every started combat and, on the runner's page only, the in-memory `starting`, `judging` and `running` sets, which cover the start of a turn before any request exists. Waiting on a person or a plan doesn't count.
- **Who sees it:** players' browsers do receive the Combat flag, plans included (read as Test Player). Accepted among friends; nothing shows in their UI.
- **Only the module rolls damage.** Workbench's auto-damage would roll on the card author's browser, with the dialog if that user has dialogs on. So `preCreateChatMessage` adds Workbench's own `noAutoDamageRoll` flag to this module's attack cards, and the module always rolls. One roller, one card, whatever anyone's settings. If Workbench drops that flag you'd see a second damage card, but not double HP, because Workbench never applies damage. Test D1 catches it; re-run D1 after any PF2e, Workbench or Toolbelt update.
- **No dialogs:** a click event with `shiftKey` equal to the user's dialog setting, because PF2e flips on Shift. `skipDialog` doesn't work.
- **A prompt nobody can click:** a roll waits for its dialog for ever, and nobody can click the runner's page. `watched` gives each stage `STEP_MS`, stops at once if a window that looks like a dialog appears, closes what appeared (a closed Modifier dialog makes the roll return with no card), and the record then says the stage may not have finished, so it goes to Rhea with the window's title and nothing repeats. PF2e's Modifier dialog is a v1 app in `ui.windows`, not in `foundry.applications.instances`, so both are watched.
- **Real targets:** `aimAt` targets on the runner's own account before each attack and damage roll, and `stopAiming` clears them after the turn. Each account has its own targets, so a GM's are never touched. That clears Workbench's targeting reminder (at "mustTarget" an untargeted Strike is cancelled outright, tested). **With automatic damage on, `markApplied` flags the module's damage card as `autoApplied` once it's made and takes Toolbelt's Target Helper row off it.** A flagged card doesn't draw PF2e's `.damage-application` buttons for players (`onRenderMessage`, in their browser only; GMs keep them). Those buttons and the row's both applied a second time after the module had applied damage, even once Toolbelt marked the row applied (tested), and Block comes too late to work: Shield Block's route is the reaction pop-up, before damage. Toolbelt fills the row from the roll's target, in a `preCreateChatMessage` hook that runs after this module's, so it comes off afterwards whatever the hook order. If Toolbelt renames its flag the row stays, and if PF2e renames the class the buttons show again; nothing else breaks. With automatic damage off, nothing is marked. A player's own cards aren't touched. Others see the runner's target mark on the token during the turn.
- **Applying** copies PF2e's Damage, Half and Double buttons (`applyFromCard`, PF2e's `applyDamageFromMessage`) for a named target: contextual clone, roll options from the card plus `origin:ally` or `origin:enemy` as PF2e adds (0.6.0), item, outcome, and the roll altered by the multiplier. It doesn't read effects that count only for one hit, because PF2e's `extractEphemeralEffects` isn't exported.
- **One run at a time:** `judge` and `doIt` each guard by request id in memory. With Auto on, the `updateCombat` hook and the submitter both reached `judge` and rolled the first attack twice, which the D1 matrix didn't catch because it didn't use Auto. D1 now includes it.
- **Only this turn on the card:** `currentRequest` is this round and turn's unfinished request, and `latestNote` only the latest finished turn's note. Both came from an old turn showing up as if it were current: a stopped request after Play it myself, and a 0 HP warning while the hero stood at 5.
- **Never twice:** `save` writes each stage to `log` before moving on, and `nextAction` reads it. `started` with no attack, `damageStarted` with no card, or `applying` with no `applied` means it can't tell, so the card stops and asks. A reload at any point resumes from there through Do it.
- **The `lythara-encounter-builder.step` hook** fires before each stage; return false to stop there. The reload tests use it.
- **Saves use `{ render: false }`** so each stage doesn't redraw the tracker. Whether that's fully quiet with PF2e HUD open isn't checked yet. **Saves send only the change:** two browsers write to a request now, so a whole copy could put back what the other just wrote.
- **A reload:** on the runner's `ready`, a request still `running` becomes `stopped` with a note, and Do it carries on from the record. A `go` or a plan left waiting is picked up.

## The brain interface
Whoever thinks for a monster (a Claude chat through the bridge now, the Claude API later) uses the same four calls, so nothing changes when the API arrives. The module can't tell them apart.
- **`api.fight.waitForEvent(cursor, maxSeconds, {generation})`.** With no generation it's a new thinker: it gets `hello` at once (the prompt from `prompt.mjs`, the schemas, the step kinds, which kinds can be carried out so far, its generation) and any older thinker is retired. Otherwise it returns the first event after `cursor` whose request still waits (`live`), holding up to `maxSeconds` (capped at 100, because `run_script` stops at 120) on the `updateCombat` hook; `{idle: true}` if nothing came. The answer's `cursor` is the event's number: the caller passes it back next time, so a dropped call loses nothing and a repeat gets the same event.
- **Events** are written by the runner only, on the Combat flag beside the request, in the same update: `turn` when a request gets its packet, `retry` after the first refusal, `replan` when a turn is asked again (it carries the reason and what's done). **Numbers are the clock, never below any number given out (`nextSeq`),** so one cursor serves every fight. An event matters only while its request waits for the plan it asks for (`state` requested, a packet, not given up, `tries` equal to the event's), so a fresh chat with cursor 0 gets only what's waiting now, never history.
- **`submitPlan(combat, requestId, plan, meta)`** stores the plan as it came, whole (`ForcedReplacement`: a merge kept keys the new plan didn't have), with `by` from `cleanMeta`. A plan from an older generation is ignored, with words; one with no generation is a GM by hand and always counts. Anything over 8,000 characters is refused unread.
- **The runner cleans and checks it in `judgeNow`:** `cleanPlan` keeps only the fields the module reads and refuses a wrong shape with a reason; then `checkPlan` for legality. **Tries are counted in one place, `reject`:** the first refusal goes back to the thinker as a `retry` event with the reason and its plan; the second puts "Couldn't do: …" on the card for the GM (`MAX_TRIES`).
- **`checkPlan(combat, requestId, plan)`** on the API answers what the runner would say and writes nothing; it needs the fight open on that page. **`reportFailure`** puts the thinker's reason on the card and stops events for that turn (`gaveUp`). **`state(combat)`** is a short read for the thinker.
- **The light:** every wait writes the world setting `brainAt` on Foundry's server clock (`game.time.serverTime`, the same in every browser; it restarts with the server, so a time ahead of now counts as not listening). The Monster Turns window shows "Angel is listening" while that's under 2 minutes old (`LISTEN_MS`), re-drawing itself when it turns grey, and a waiting request gets "Angel isn't listening. Play it yourself, or in the chat say go." A chat can't be woken from outside, so that's the honest fallback. **The generation lives apart, in `brain`, and only a hello writes it** (0.8.2): when a wait renewed both together, a page's copy of `brain` a moment old could let an old chat's renewal land just after a new chat's hello and put the old generation back, undoing the takeover (found by the bridge 0.3.0 review).
- **Plans from outside are data.** `cleanPlan` drops unknown keys, checks ids and labels by pattern, strips control characters and caps text. The card escapes everything it shows.

## What a monster perceives
Worked out by the module, on the runner, with the fight open. Visioner can't answer it alone: with its automatic system off it says "observed" for a pair with no record, walls or no walls, and a monster token isn't a vision source (tested). Rules: Perception and Detection (https://2e.aonprd.com/Rules.aspx?ID=2400), Light (https://2e.aonprd.com/Rules.aspx?ID=2401).
- **Inputs, per pair (`sense`):** `actor.perception.senses` plus hearing, which PF2e doesn't list on NPCs and the rules give no fixed range; core's `testCollision` centre to centre for sight and for sound; the light at the target; blinded, dazzled, deafened on the monster; invisible and concealed on the target; Visioner's stored state.
- **Light (`lightOn`, `lightAt`):** the scene's level by PF2e's own thresholds (`ScenePF2e.isBright` at 3/4, `isDark` at 1/4), raised by any source whose shape holds the point. A darkness source wins. `GlobalLightSource` doesn't count: PF2e's rule-based levels decide what the scene gives.
- **Visioner on top:** a stored Concealed, Hidden, Undetected or Unnoticed counts if it's worse than what the senses say. A stored Observed says nothing, because it's also the answer for no record. With its automatic system on, its answer is used directly.
- **Hearing makes most things Hidden:** a creature it can't see but can hear is hidden at its exact square, however far, unless a wall blocks sound (Survey Sheet's trunks don't) or Visioner has it undetected from a Sneak. That's the rules with no made-up limit.
- **Who counts:** tokens on the scene that are creatures, not core-hidden, and `isEnemyOf` the monster, in the fight or not. Allies are `isAllyOf`, known by default; a brief's "no shared knowledge" isn't built.
- **The packet (`packetOf`):** observed and concealed show square, size, gear, visible conditions, health word, distance, cover. Hidden shows the square only. Undetected isn't listed; if it has memory, a `memory` line with `lastSeen` and round. Unnoticed: nothing. Everything about others goes through `packetOf`, field by field, so HP, AC, saves, level and names can't get in. `you` is the monster's own sheet. Text in it is data, never instruction. `schema` is checked by whoever reads it.
- **Health words** are PF2e HUD's: its `healthStatusData` setting, or its default list with the markers it would give them.
- **Gear** uses the item's source name, because PF2e builds "+1 Striking Longsword" from the runes.
- **Ground (`groundAround`):** a text map 10 squares around it, from the same `readMap` model the builder uses. Tokens aren't marked, or an unseen one would show as a gap. Allies and what it perceives have squares of their own.
- **Actions (`actionsFor`):** Workbench's sum: 3, plus quickened, less the largest of slowed, stunned and Workbench's `stunReduction` for this round. Workbench lowers stunned at the start of the turn, so reading stunned alone would miss it (tested).
- **Labels and memory:** E and M labels last the whole fight and are given out when first needed. Memory updates at every turn change for every ticked monster, not only on its own turn.
- **A plan can name only labels in its request that it still perceives** (`gather`). `flatDC` adds the check to the step: DC 5 concealed, DC 11 hidden. It's rolled first and logged, and a failure spends the action with no attack (`nextAction`). PF2e and Visioner don't roll it. Undetected can't be targeted yet: picking a square isn't built.
- **Strike ids** come from `strikeIds`: a thrown dagger shares its slug with the melee one, so the second gets `-ranged`.
- **Cover with no dialog works.** Visioner's auto-cover applied on a real Strike by the Shift route: AC 11 became DC 15 behind a test wall, and behind one real trunk with a Shortbow (tested 2026-11-06). So nothing needs passing on, and `getAutoCoverState` is what the packet shows.
- **Not on the fight scene:** `perceived` refuses, and a turn's request says so instead of giving silent wrong answers.

## Hooks must return nothing
Core fires `canvasReady` with `Hooks.call`, where a handler returning `false` stops every later handler, from every module. 0.1.0 to 0.2.4 had `c => markReady(id)`, and `Set#delete` returns false for an id it doesn't hold, so on every client the 20 `canvasReady` handlers registered after it never ran. Every hook here has a block body, and `unit.mjs` fails if one doesn't.
